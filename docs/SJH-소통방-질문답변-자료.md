## 1. 정보 소통방 안내봇 — "훈련"이 아니라 "규칙"

**확인 경로**: `frontend/src/services/guideBot.ts` (890줄) · `frontend/src/pages/TalkPage.vue`

### 1-1. 왜 LLM을 안 썼나 — 세 가지 이유

1. **저장소에 LLM도 API 키도 없다.** 붙인 적이 없다.
2. **발표장에서 네트워크가 막히면 대화창이 통째로 빈 화면이 된다.** 그 위험을 지지 않기로
   했다 (기획자 결정, 09-03 15:30).
3. **복지 자격을 잘못 안내하는 것이 답을 못 하는 것보다 훨씬 나쁘다.** 헌법 원칙 I(근거 기반).
   신청 서류·대기 기간·본인부담금 액수는 우리가 모르는 영역이고, LLM은 이런 걸 그럴듯하게
   지어낸다.

### 1-2. 그래서 무엇을 만들었나 — 숫자

| 항목 | 수 |
|---|---|
| 규칙 | **69개** |
| 주제 묶음 | **12개** |
| 화면에 펼치는 질문(`asks`) | **102개** |
| 자유 입력을 잡는 열쇳말(`keys`) | **340개** |

묶음 12개와 규칙 수:
진단 시작하기 8 · 문항에 답하기 6 · 결과 읽기 7 · 판정 불가와 정확도 6 · 신청처 찾기 8 ·
어떤 서비스인가 6 · 개인정보와 저장 5 · 마이페이지와 즐겨찾기 3 · 후기 소통방 5 ·
화면 사용법 5 · 마음이 힘들 때 4 · 이 서비스에 대해 6

### 1-3. 지식의 출처 — "여기서 새로 만든 사실은 없다"

답에 쓰인 숫자와 표현은 전부 다음에서 가져왔다:

- `CLAUDE.md` — 등급 표시 명칭, 척도 방향, 실측 수치
- `specs/001-care-burden-map/spec.md` — 기능 요구사항
- 실제 화면에 쓰인 문구

특히 **등급 이름은 화면과 한 글자도 다르지 않게** 상수로 묶어 뒀다
(`최고부담군 · 고부담군 · 중간부담군 · 저부담군 · 부담 없음`).

### 1-4. 어떻게 답을 고르는가 — 2단계

```
① 화면에서 누른 질문  → 정규화 후 글자 그대로 맞춰 그 규칙으로 (BY_ASK 맵)
② 직접 적은 말       → 열쇳말 부분 일치, 가장 긴 열쇳말이 이긴다
③ 아무것도 안 걸리면 → fallback (지어내지 않고 사람에게 넘긴다)
```

정규화는 대소문자·띄어쓰기·문장부호(`? ! . , " ' ( ) ·`)를 지운 뒤 비교한다.

**왜 "가장 긴 열쇳말"인가** — `판정 불가`가 `진단`보다 구체적이니 먼저 잡혀야 한다.
길이로 겨루면 이게 자동으로 된다.

**왜 ①이 따로 있는가 — 실제로 있었던 사고** (09-03 15:55)
> "형제자매도 지원을 받을 수 있나요?" 가 `받을 수 있` 이라는 열쇳말에 걸려
> 엉뚱한 **이용 대상 안내**로 샜다. 화면에서 누른 질문은 글자 그대로 맞추게 바꿔서
> 구조적으로 막았다.

**화면의 질문 목록도 규칙 표에서 만든다** (`TOPICS`). 목록을 손으로 따로 적으면 규칙과
갈라져서 **"눌렀는데 모르겠다고 답하는"** 일이 생긴다. 실제로 그랬고, 아예 갈라질 수 없게
한 벌에서 뽑는다.

### 1-5. 모를 때 — 지어내지 않는다

> "그건 제가 확실히 알지 못합니다. 잘못 알려 드리느니 모른다고 말씀드리는 편이 낫겠습니다.
> 이 서비스 안의 일(진단·결과·신청처·개인정보·즐겨찾기·후기)은 안내해 드릴 수 있고,
> 그 밖의 것은 **지역 발달장애인지원센터**에 문의하시면 정확합니다."

명시적으로 "모른다"고 답하는 영역: 신청 서류 · 대기 기간 · 본인부담금 액수 ·
기관별 프로그램 · 활동지원/장애등록/수당 · 가족 지원 목록 · 이사 시 서비스 승계.

### 1-6. 검증

`frontend/tests/unit/rooms.test.ts` — **18개 테스트 통과**.
화면 질문 **102개 전수**를 눌러 보고 하나도 fallback으로 새지 않는 것을 확인한다.

### 1-7. 나중에 LLM을 붙인다면

`answer()` 를 그대로 두고, **규칙에 걸리지 않은 말만** 서버에 물어보도록 감싸면 된다.
화면은 바꿀 필요가 없다 — 코드에 그 자리를 주석으로 남겨 뒀다.

## 2. 부담 진단 모델 — 이쪽은 실제로 학습시켰다

**확인 경로**: `docs/HG-모델-성능-리포트.md` · `docs/모델-학습-방법.md` · `models/model_v1.json`

### 2-1. 무엇으로 학습했나

- **데이터**: 2024 발달장애인 일과 삶 실태조사 **3,000가구**
- **알고리즘**: 다항 로지스틱 회귀 (multinomial logistic regression)
- **입력**: 7문항 → 원-핫 **53열**
- **출력**: 5구간
- **버전**: 모델 `v1.0.0` · 문항집합 `qs-v1.0.0` · 학습 시각 `2026-09-01T11:51:58`

```python
OneHotEncoder(handle_unknown='ignore')                      # 7문항 → 53열
LogisticRegression(max_iter=2000, random_state=20260901)    # 5클래스 다항 분류
```

### 2-2. 데이터를 어떻게 나눴나

```
3,000가구
  ① 행 내용 전체를 MD5 해시 → 그 순서로 정렬
  ② 부담 구간 비율을 유지하며 80 : 20 (층화)
      train 2,398건 ── 학습·문항선별·임계값을 전부 여기서만
      test    602건 ── 봉인. 모든 결정이 끝난 뒤 단 한 번만
  ③ train 을 다시 구간 비율 유지하며 5등분 (층화 5-fold)
      fold 483 / 481 / 478 / 478 / 478
```

**해시로 정렬하는 이유** — 나이나 지역 같은 실제 값으로 자르면 test가 특정 특성에 쏠린다.
해시는 내용과 무관하게 흩어지므로 그 쏠림이 없다.

**분할은 코드가 아니라 DB에 있다** — `cb_dataset_v1` 의 `split` · `cv_fold` 컬럼.
누가 언제 어떤 코드로 돌려도 같은 가구가 같은 폴드에 들어간다 (헌법 원칙 IV, FR-012).

**왜 층화인가** — `부담없음` 이 train 2,398건 중 **61건(2.5%)** 뿐이다. 무작위 5분할이면
폴드마다 8~17건으로 들쭉날쭉해 macro F1이 크게 튄다. 층화로 모든 폴드가 12~13건씩 갖는다.
폴드 간 비율 편차 **최대 0.20%p**.

### 2-3. 설계 선택 세 가지

| 선택 | 이유 |
|---|---|
| 결측을 채우지 않고 `-1` 로 넣는다 | 이 데이터의 결측은 누락이 아니라 분기 문항의 "해당 없음"이다. 대치하면 정보가 훼손된다 |
| 원-핫은 **폴드마다 학습 부분으로만** fit | 전체로 fit 하면 교차검증이 오염된다 |
| 1·2단계 확률에 **1.1** 을 곱한다 | 고부담을 놓치는 것이 가장 비싼 오류다. **이 값은 사람이 정하지 않았다** — "재현율 0.73 이상 중 macro F1 최대" 규칙이 자동으로 골랐다 |

### 2-4. 왜 이 알고리즘인가 — 계열 비교

38변수 전체로 같은 폴드·같은 지표로 붙였다.

| 계열 | macro F1 | 고부담 재현율 | |
|---|---|---|---|
| **다항 로지스틱** | **0.3180** | **0.7636** | 채택 |
| 랜덤 포레스트 | 0.2894 | 0.7552 | |
| 엑스트라 트리 | 0.2668 | 0.7544 | |

트리 계열이 선형 모델에 졌다. 2,398건 표본에서 트리가 규칙을 잘게 쪼개며 과적합한 결과로 본다.

### 2-5. 성능 — 솔직하게 말할 숫자

- **5구간 정확도 47.8%** (무작위 20%, 최빈값 찍기 38.7%)
- **"지원이 필요한 사람인가" 2분류는 정확도 69.6%, 재현율 77.3%**
- **부담이 큰 사람을 "부담 없음"으로 판정한 위험한 실수는 test 602건 중 0건**
- test(47.8%)가 교차검증(46.3%)보다 약간 좋다 — 과적합이 심하지 않다는 건강한 신호

정확도를 물으면 이렇게 답한다:
> "솔직히 완벽하지 않습니다. 특히 **낮은 쪽 구간은 거의 못 가려냅니다** — `부담 없음`은
> 학습 데이터에 61건뿐이라 모델이 만들어내지 못하는 등급입니다. 다만 이 서비스가 실제로
> 물어야 하는 건 '몇 단계인가'가 아니라 '지원이 필요한 사람인가'이고, 그건 **10명 중 7~8명**
> 잡아냅니다. 그리고 **부담이 큰 분을 '부담 없음'으로 돌려보낸 적은 한 번도 없습니다.**"

## 3. 이용후기 소통방 — 서버에 저장된다

| | |
|---|---|
| **저장 위치** | MySQL 테이블 **`cb_facility_review_v1`** |
| **서버** | `mis.iptime.org:13306` · DB `ABC8pioneer3` (`.env` 의 `DB_HOST`/`DB_PORT`/`DB_NAME`) |

**왜 서버인가** — 글이 공유되어야 '소통'이 된다. 브라우저에만 두면 남이 못 읽는다.

### 3-2. 무엇이 저장되나 — 컬럼 8개

| 컬럼 | 내용 |
|---|---|
| `review_id` | 글 번호 |
| `facility_id` | 어느 기관 글인지 |
| `nickname` | **스스로 적은 별명** (최대 20자). 실명 요구 안 함. 안 적으면 "이름 없는 보호자" |
| `rating` | 별점 1~5 |
| `body` | 본문 (최대 600자, 최소 5자) |
| `owner_token` | **글 하나의 삭제 열쇠** (§3-3) |
| `created_at` | 작성 시각 |
| `is_hidden` | 신고 처리용 — **지우지 않고 가린다** |

### 3-3. 저장하지 **않는** 것 — 컬럼 자체를 두지 않았다

이름 · 연락처 · 계정 · **IP** · 위경도 · `session_id`.
헌법 원칙 III을 "안 쓴다"가 아니라 **"쓸 자리를 안 만든다"** 로 지켰다.

**`owner_token` 은 사람이 아니라 글을 가리킨다**
- 서버가 글을 저장할 때 `randomUUID()` 로 만들어 **한 번만** 돌려준다. 다시 알려주지 않는다.
- 브라우저가 `localStorage` 의 `cb.reviewTokens` 에 `{글번호: 토큰}` 으로 넣어 둔다.
- 지울 때 `x-owner-token` 헤더로 되돌려 주면 그 글만 지워진다.
- **글마다 새로 만든다** → 서버는 이 값으로 사람을 찾을 수도, 같은 사람의 글끼리 묶을 수도 없다.
- 브라우저 저장소를 지우면 본인도 그 글을 못 지운다 (그 대가로 익명이 성립한다).

### 3-4. 개인정보가 섞여 들어오는 것을 막는다

본문·별명에 **휴대폰번호 · 주민등록번호 · 이메일** 꼴이 있으면 **저장하지 않고 되돌려 보낸다.**

> "전화번호·이메일·주민등록번호처럼 개인을 알아볼 수 있는 정보는 담을 수 없습니다.
> 지우고 다시 올려 주세요."

**몰래 지우고 저장하지 않는 이유** — 그러면 본인이 무엇이 지워졌는지 모른다.
무엇이 문제인지 말해 주고 고치게 한다.

### 3-5. 다른 저장소와 이어 붙일 수 없다 (FR-032)

후기 테이블에는 `cb_event_log_v1`(익명 로그)·`cb_training_response_v1`(학습 응답)과
**조인할 수 있는 컬럼이 없다.** `session_id` 를 여기에 두지 않은 이유다.

`db/scripts/verify.js` 가 이것을 자동 검증한다 (`npm run verify` · `check_project.sh check`).

## 4. 대조표 — 소통방 두 곳은 저장 위치가 반대다

| | **정보 소통방** (`/talk`) | **이용후기 소통방** (`/reviews`) |
|---|---|---|
| 무엇 | 안내봇과 묻고 답하기 | 기관 이용 후기를 서로 나누기 |
| 저장 위치 | **브라우저만** (`localStorage` 의 `cb.talk`) | **서버 DB** (`cb_facility_review_v1`) |
| 보관량 | 최근 40건 | 제한 없음 (`is_hidden` 으로 가릴 뿐 지우지 않음) |
| 서버로 가나 | **대화 내용은 안 간다** | 간다 (그게 목적) |
| 지우기 | 화면의 "대화 지우기" 한 번 | 쓴 브라우저에서만 (`owner_token`) |
| 왜 이렇게 | 남이 읽을 이유가 없다 | 공유돼야 '소통'이 된다 |

### 짚고 넘어갈 것 — 대화 "내용"과 "사건"은 다르다

정보 소통방에서 메시지를 보내면 **`TALK_MESSAGE` 라는 사건 종류 하나**가 익명 이벤트
로그(`cb_event_log_v1`)에 남는다. **무엇을 적었는지는 가지 않는다** — 그 테이블에는
자유 입력 텍스트를 담을 컬럼 자체가 없다(FR-028). "몇 명이 소통방을 썼나"를 세기 위한 것이다.

봇 스스로도 이렇게 답한다:
> "이 대화는 지금 쓰시는 브라우저 안에만 남고 서버로 보내지 않습니다.
> 아래 '대화 지우기'를 누르시면 바로 없어집니다."

## 5. 꼬리 질문 대비

**Q. GPT나 ChatGPT를 쓴 건가요?**
> 아닙니다. 이 저장소에는 LLM도 API 키도 없습니다. 소통방 답은 전부 우리가 쓴 규칙
> 69개에서 나오고, 진단은 우리가 학습시킨 로지스틱 회귀 모델이 냅니다.

**Q. 그럼 소통방이 무슨 AI인가요?**
> 엄밀히는 AI라고 부르기 어렵습니다. **안내봇**이 맞는 이름이고 화면에도 그렇게 적혀
> 있습니다. 대신 **못 하는 걸 못 한다고 말하는 것**은 확실히 합니다 — 모르는 질문에
> 그럴듯한 답을 지어내지 않습니다.

**Q. 학습 데이터는 어디서 구했나요?**
> 2024 발달장애인 일과 삶 실태조사 3,000가구입니다. 이용자에게 받은 데이터가 아닙니다.

**Q. 이용자가 낸 답이 모델 학습에 쓰이나요?**
> **동의하신 경우에만** `cb_training_response_v1` 에 들어갑니다(FR-031). 별명·나이·
> 돌봄 대상 수 같은 사전 입력 값과 자유 입력 텍스트는 **그 테이블에 컬럼이 없습니다.**
> 제출 시각도 초 단위로 잘라 저장해 시각 대조로 사람을 좁힐 수 없게 했습니다.

**Q. 후기에 악성 글이 올라오면요?**
> `is_hidden` 으로 가립니다. 지우지 않고 가리는 이유는 기록을 남기기 위해서입니다.
> 다만 **신고 화면은 아직 없습니다** — 지금은 DB에서 직접 바꿔야 합니다.

**Q. 후기를 쓴 사람이 누군지 알 수 있나요?**
> 없습니다. 이름·연락처·계정·IP를 담을 컬럼 자체를 두지 않았습니다. `owner_token` 은
> 글 하나의 삭제 열쇠일 뿐이고 글마다 새로 만들어서, 같은 사람의 글끼리 묶는 것도
> 불가능합니다.
