작성 오현근 · 2026-09-02 16:50 KST · 브랜치 `experiment/HG-model`
대상 모델 `v1.0.0` (7문항 · 다항 로지스틱 · 원-핫 53열)

> 이 문서는 개별 기록들을 하나로 모은 것이다. 각 실험의 자세한 과정은
> 표의 '기록' 열에 적힌 문서에 있다. **숫자는 전부 그 문서에서 그대로 옮겼다.**

## 0. 한 장 요약

배포본을 개선해 보려고 여섯 가지를 시도했다. **여섯 번 다 기각됐다.**
그 결과 `v1.0.0` 이 이 데이터에서 뽑을 수 있는 것에 근접해 있다는 결론에 이르렀다.

```
모델 쪽    정규화 튜닝 · 서열 모델 · 문항 14개 · 변수 38개   → 전부 기각
데이터 쪽  더 모으기 · 라벨 정의 바꾸기                      → 전부 기각
남은 것    지금 설문에 없는 변수를 새로 모으기               → 이번 범위 밖
```

이건 실패의 기록이 아니라 **"여기서 멈추는 것이 합리적"이라는 근거의 기록**이다.

## 3. 하나씩

### 3.1 문항 14개 (v1.1.0) — 폐기

문항을 두 배로 늘렸다. **성능은 그대로였고(+0.0004) 판정 불가만 2.49% → 4.20% 로 늘었다.**
이용자에게 두 배 묻고 얻은 것이 "모르겠다는 답이 1.7배" 였다.

부작용도 있었다. 실험 모델이 최상위 `models/` 에 잠시 올라가 있던 사이
`cb_model_version_v1` 의 v1.0.0 행이 14문항 평가 결과로 덮였다(6.4 참조).
이 사고가 학습 라이브러리에 `models/runs/` 분리와 `promote` 단계를 만든 계기가 됐다.

사용자 결정으로 브랜치와 함께 폐기했다.

### 3.2 정규화 튜닝 — 기각

`penalty`(l1·l2)와 `C` 를 15가지로 훑었다.

```
l2 C=10   폴드별 차이(C=10 − C=1)  +0.0206 +0.0043 −0.0039 +0.0126 +0.0664
          평균 +0.0200 · 표준편차 ±0.0275 · 4/5 폴드 승 · t = 1.63
```

5개 폴드에서 95% 로 말하려면 **|t| ≥ 2.776** 이 필요하다. 1.63 은 한참 못 미치고,
평균의 대부분을 **폴드 하나(+0.0664)** 가 끌고 있다.

성능보다 중요한 게 부작용이었다. C 를 키우면 **소수 표본이 만든 계수가 커진다.**
3명이 고른 선택지의 계수가 0.60 → 1.25 로 두 배가 됐다. 세 사람의 답이
다음 이용자의 판정을 두 배로 좌우한다는 뜻이라 이 서비스에서는 받아들이기 어렵다.

L1(계수를 0으로 누르는 쪽)도 봤지만 **누르는 기준이 표본 수가 아니라 설명력**이었다.
10명 이하 선택지의 25% 를 0으로 만드는 동안 200명 넘는 선택지도 4% 를 0으로 만들었다.
목적(소수 표본 억제)에 맞지 않아 기각했다.

### 3.3 서열 모델 — 기각

"다섯 중 하나" 를 "예/아니오 네 번"(`P(y≤1)` … `P(y≤4)`)으로 바꿔 학습하고 다시 합쳤다.
순서를 아는 모델이니 **크게 빗나가는 오류**가 줄 것으로 기대했다.

| 지표 | 지금 | 서열 | 차이 | t |
|---|---|---|---|---|
| macro F1 | 0.3364 | 0.3337 | −0.0028 | −0.36 |
| 고부담 재현율 | 0.7844 | 0.7821 | −0.0023 | −0.74 |
| 두 칸 이상 오류 | 9.8% | 9.5% | −0.0025 | −1.81 |
| 단조성 위반 | — | 0.79% | | |

미리 정한 네 조건 중 **둘(재현율·F1)을 못 넘겨 기각**했다.
두 칸 오류가 줄긴 했지만 그 폭은 2,398명 중 **약 5명**이고 t 도 부족하다.

부수 소득이 하나 있었다. 계획 단계에서 "서열 모델은 확률이 퍼져 판정 불가가
2% → 11% 로 튈 수 있다" 고 걱정했는데 **반대였다.** 서열 쪽 최대확률 중앙값이
0.4856 으로 오히려 높아 문턱 아래가 1.33%(지금 2.00%)였다. 추측을 실측으로 지웠다.

### 3.4 변수 38개 전부 — 기각

"문항이 부족해서 성능이 안 나오는 것" 인지 보려고 쓸 수 있는 변수를 전부 넣었다.

| | macro F1 | 재현율 | 정확도 | 고부담 여부 정확도 |
|---|---|---|---|---|
| 7문항 (배포본) | **0.3364** | 0.7844 | **46.3%** | **69.4%** |
| 38변수 로지스틱 | 0.3141 | 0.7322 | 41.3% | 65.5% |
| 38변수 랜덤포레스트 | 0.2825 | 0.7928 | 45.8% | 69.1% |

**변수를 5배 넣어도 오르지 않는다.** 로지스틱이 내려간 건 과적합으로 설명되지만,
그 걱정이 없는 랜덤포레스트도 7문항과 같은 자리다.
**나머지 31개 변수에 더 들어 있는 정보가 사실상 없다.**

### 3.5 학습곡선 — 평평

폴드마다 학습에 쓰는 건수를 잘라가며 재웠다(100% = 1,918건).

| 학습량 | 재현율 | 고부담 여부 정확도 |
|---|---|---|
| 20% (384건) | 0.7580 | 66.9% |
| 40% (767건) | 0.7680 | 68.2% |
| 60% (1,151건) | 0.7806 | 68.3% |
| 80% (1,535건) | 0.7864 | 68.8% |
| **100% (1,918건)** | **0.7844** | **69.4%** |

마지막 구간 **+0.7%p**, 폴드 간 표준편차 **2.9%p**. 증가폭이 잡음보다 작다.
**384건만으로 66.9% 가 나온다**는 게 이 표의 요점이다 —
이 문제는 데이터가 모자라서 못 푸는 문제가 아니다.

### 3.6 라벨 재정의 — 기각

서비스 화면에서 3·4·5 는 완전히 같다(경고 없음 · 즉시 안내 없음).
61명뿐인 5번군을 가르느라 손해를 보는 게 아닌지 의심스러워 정답 라벨만 바꿔 학습했다.
가중치로 유리하게 고르지 못하게 **재현율을 0.7843 으로 맞춘 뒤** 정확도를 비교했다.

| 라벨 정의 | 재현율 | 고부담 여부 정확도 | 기준 대비 |
|---|---|---|---|
| 5구간 (지금) | 0.7843 | 69.4% | ±0.0%p |
| 3구간 1/2/그외 | 0.7920 | 69.3% | −0.1%p |
| 2분류 고부담/아님 | 0.7989 | **70.2%** | +0.8%p |

2분류가 가장 낫지만 **+0.8%p 는 폴드 간 표준편차 2.9%p 보다 작다.**
스펙(FR-010a 표시 명칭 · SC-004 · SC-005)을 고칠 값이 아니다. **5구간 유지.**

## 4. 왜 여섯 번 다 안 열렸나

라벨 품질을 따로 점검해 보니(`HG_라벨품질-점검.md`) 그림이 맞아떨어진다.

**① 라벨은 잡음이 아니다.** 상식적인 방향으로 여러 변수와 붙는다.

```
help_needed_hours              +0.442   도움이 많이 필요할수록 부담이 크다   ✓
understands_work_meaning       −0.429   이해하지 못할수록 부담이 크다        ✓
family_support_for_employment  +0.247   가족 지지가 낮을수록 부담이 크다      ✓
daily_routine_satisfaction     +0.241   일과를 싫어할수록 부담이 크다        ✓
```
(배포 문항 4개는 선택지 문구까지 대조해 방향을 확인했다.)

**② 그런데 같은 답을 낸 사람끼리 갈린다.** 7문항 기준 2명 이상인 조합 326개 중
**80.1% 에서 라벨이 갈리고, 62.9% 는 고부담이냐 아니냐에서조차 갈린다.**
4칸 갈린 조합이 7개다 — 똑같이 답했는데 한 명은 최고부담군, 한 명은 부담 없음이다.

**③ 변수를 늘려도 안 오르고, 데이터를 늘려도 안 오른다.** (3.4 · 3.5)

셋을 합치면 이렇게 된다.

> **라벨이 망가진 것도 아니고, 문항이 모자란 것도 아니다.
> 이 설문 도구로 설명되는 부담의 몫이 원래 작다.**

부담은 당사자의 상태만으로 정해지지 않는다. 보호자 본인의 건강, 소득, 실제 돌봄 시간,
형제자매의 분담, 거주지의 서비스 접근성 — 이 설문에 **없는** 것들이 크게 작용한다.
그래서 안에 있는 정보를 아무리 잘 짜내도 벽에 부딪힌다.

## 5. 그래서 남은 것

| 갈래 | 상태 |
|---|---|
| 알고리즘·초매개변수 | **닫힘** — 실험 2·3·4 |
| 문항 늘리기 | **닫힘** — 실험 1·4 |
| 데이터 더 모으기 | **닫힘** — 실험 5 |
| 라벨 정의 바꾸기 | **닫힘** — 실험 6 |
| **지금 설문에 없는 변수를 새로 모으기** | **유일하게 열려 있음 · 이번 범위 밖** |

마지막 항목은 분석으로 만들 수 없고 **다음 조사에서 문항으로 넣어야** 나온다.
이번 프로젝트에서 할 수 있는 일이 아니다.

### 5.1 나쁜 소식만은 아니다

성능을 더 못 올린다는 건 이미 내린 설계 결정이 옳았다는 뜻이기도 하다.

- **판정 불가 안내**가 그 답이었다. 못 맞히는 사람을 억지로 분류하는 대신
  "판정할 수 없다" 고 말하고 상담으로 넘기는 길을 이미 만들어 뒀다.
- **고부담 재현율 0.77~0.78** 로 SC-005 하한(0.70)을 넘는다. 이 서비스가 지켜야 할 것은
  '정확히 몇 번군인지' 가 아니라 **'무거운 분을 놓치지 않는 것'** 이고, 그건 되고 있다.
- 결정 가중치 `[1.1, 1.1, 1, 1, 1]` 도 그 목적에 맞춰 이미 조여져 있다.

**결론은 "더 할 게 없다" 가 아니라 "모델 성능 쪽 작업은 여기서 멈추는 것이 합리적" 이다.**

## 6. 실험 중에 정정한 것들

실험만큼이나 이쪽이 값어치 있다. 남겨 두지 않으면 다시 틀린다.

### 6.1 SEED — 42 가 아니라 20260901

라이브러리 이전 계획서에 `SEED = 42` 로 적혀 있었는데 원본 `ml/train.py` 는 `20260901` 이었다.
그대로 갔으면 **같은 데이터에서 다른 모델이 나와** 이전 검증 자체가 무의미해질 뻔했다.
`config.py` 에 못 박고 회귀 테스트를 붙였다.

### 6.2 기여 요인을 엉뚱한 구간으로 계산하던 것

`saabas` 는 클래스를 안 주면 **아티팩트의 결정 가중치**로 구간을 다시 고른다.
그런데 우리는 설정에서 온 정책 가중치로 골랐다. 두 값이 갈리면 화면에 나가는
"이래서 이렇게 판정했습니다" 가 실제 판정과 다른 구간의 설명이 된다.
실패하는 테스트를 먼저 쓰고 `cls_idx` 를 넘기도록 고쳤다.

### 6.3 L1 재현율 0.7498 은 잘못 읽은 값

그리드는 조합마다 결정 가중치를 다시 튜닝한다. 가중치를 배포본 값으로 고정하면
같은 설정의 재현율이 **0.7882** 다. 튜닝 결과 표를 그대로 인용하면 안 된다는 교훈.

### 6.4 DB 의 v1.0.0 성능 기록이 14문항 결과로 덮여 있던 것

```
정정 전  F1 0.3420 · 재현율 0.7669 · 판정불가 0.0415   ← 14문항 결과
정정 후  F1 0.3416 · 재현율 0.7730 · 판정불가 0.0249   ← 진짜 7문항 v1.0.0
```

값을 손으로 고치지 않고 `MODEL_VERSION=v1.0.0` 으로 **같은 코드 경로에서 다시 만들어** 넣었다.

### 6.5 "천장 70.6%" 는 라벨이 나쁘다는 증거가 아니다

중복 응답으로 센 천장은 **7문항 시야의 천장**이다. 38변수로 보면 2,398명 전원이
유일한 조합이라 이 방식으로는 천장을 셀 수조차 없다.

### 6.6 "천장 85.0% 까지 15%p 남았다" 도 오해

천장 계산은 1명짜리 조합을 자동으로 '맞힌 것' 으로 센다. 7문항 조합 1,156개 중
**830개가 1명짜리**다. 그 한 명은 외워야만 맞히는데 외우는 건 일반화가 아니다.
**느슨한 상한이지 남은 여지가 아니다.**

## 7. 실험을 이렇게 했다 — 다음 사람이 이어받으려면

여섯 번 모두 같은 규칙을 지켰다. 결과보다 이 규칙이 오래 남을 것이다.

1. **판정 기준을 돌리기 전에 적는다.** 결과를 보고 기준을 옮기면 실험이 아니라 사후 합리화다.
2. **`cv_fold` 로 고정된 5-fold 만 쓴다.** 분할을 새로 만들면 이전 결과와 비교가 안 된다(원칙 IV).
3. **test 602건은 손대지 않는다.** 모든 결정이 끝난 뒤 단 한 번 쓰는 몫이다.
4. **짝지어 비교한다.** 같은 폴드끼리 빼면 폴드 자체의 난이도가 상쇄된다.
   5개 폴드에서 95% 로 말하려면 **|t| ≥ 2.776** 이다. 여섯 번 중 이걸 넘긴 실험은 **하나도 없다.**
5. **결정 가중치를 유리하게 고르지 못하게 한다.** 고정하거나, 재현율을 같은 값에 맞춘 뒤 비교한다.
6. **한 번에 한 가지만 바꾼다.** 문항과 알고리즘을 같이 바꾸면 원인을 못 가린다.
7. **스냅샷만 읽는다.** DB · `models/` · `main` 브랜치 · 실행 중인 서비스를 건드리지 않는다.
8. **실패도 그대로 남긴다.** 특히 6장의 정정들.
