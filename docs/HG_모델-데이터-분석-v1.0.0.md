> **공식 파이프라인 수치와 다른 이유** — `ml/train.py evaluate` 가 DB에 기록하는 공식 값은
> **macro F1 0.3416 · 재현율 0.7730** 이다. 이 문서의 0.3470·0.7736 과 차이가 나는 것은
> 계산 범위 때문이다. 공식 값은 **판정 불가 15건을 포함한 test 602건 전체**로 계산하고,
> 이 문서의 표는 **판정된 587건만**으로 계산한다(혼동행렬과 숫자를 맞추기 위해).
> 두 값 모두 맞으며 **발표·기록에는 공식 값(0.3416 / 0.7730)을 쓴다.**
> 판정 불가군의 오분류율 0.867 vs 판정군 0.513 은 양쪽이 정확히 일치한다.

**읽어야 할 세 가지**

1. **5번 구간은 한 건도 못 맞힌다.** test 15건 중 정답 0건. 학습 데이터에 77건(2.6%)뿐이라
   예측된 적이 거의 없다(전체 587건 중 5번으로 예측한 것은 **1건**). 표시 명칭에 "부담 없음"이
   있지만 **실질적으로 나오지 않는 구간**이다
2. **오차가 인접 구간에 몰려 있다.** 실제 1번을 2번으로 본 것이 59건, 실제 3번을 2번으로 본 것이
   73건이다. **정반대로 틀리는 경우는 드물다** — 실제 1번을 4·5번으로 본 것은 89건 중 1건뿐이다.
   구간을 못 맞혀도 방향은 맞는다는 뜻이라, 안내 목적에서는 치명적이지 않다
3. **고부담을 놓치는 비율이 낮다.** 재현율 0.7736 — 실제 고부담 318명 중 246명을 잡는다

## 5. 판정 불가

```
확신도 tau_conf   0.323917   최대 클래스 확률이 이보다 낮으면 판정 불가
희소성 tau_dens  -2.434272   응답 조합의 로그 빈도 평균이 이보다 낮으면 판정 불가
```

두 조건은 **OR** 다. 하나만 걸려도 판정 불가다.

| 구분 | 건수 | 비율 |
|---|---|---|
| 전체 3,000건 | 60건 | 2.00% |
| ㄴ 희소성만 | 32건 | |
| ㄴ 확신 부족만 | 28건 | |
| ㄴ 둘 다 | **0건** | |
| train 2,398건 | 45건 | 1.88% |
| test 602건 | 15건 | **2.49%** |

**두 조건이 겹치는 사례가 하나도 없다.** 서로 다른 실패를 잡고 있다는 뜻이라, 유형을 나눠
설명하는 설계가 데이터로도 뒷받침된다.

### SC-016 검증 — 걸러낸 것이 실제로 더 틀리는가

| 집단 | 오분류율 |
|---|---|
| test 판정 불가군 (15건) | **0.8667** |
| test 판정군 (587건) | 0.5128 |

**판정 불가로 뺀 사람들이 실제로 훨씬 많이 틀린다.** 임계값이 제 역할을 한다.

### 확인이 필요한 차이

`uncertainty_v1.json` 에 학습 당시 기록된 발생률은 **3.00%** 인데, 같은 임계값으로 train 을
다시 계산하면 **1.88%** 다. 유력한 설명은 **기록값이 교차검증(폴드 밖) 예측 기준이고 재계산은
전체 train 으로 적합한 최종 모델 기준**이라는 것이다 — 후자가 더 자신 있게 답하므로 판정 불가가
줄어든다. 다만 **확인하지 않은 추정**이므로 그대로 인용하지 말 것.

운영에서 실제로 보게 될 값은 **2.0~2.5%** 다.

## 7. 왜 정확도가 48%인가 — 모델 탓이 아니다

발표에서 가장 나올 만한 질문이다. **정답을 가리고 군집화**해서 답을 만들어 두었다.

| 지표 | 실측 | 뜻 |
|---|---|---|
| 실루엣 계수 | **0.12** | 0.25 미만 = 뚜렷한 덩어리 구조 없음 |
| 부담 구간과의 일치도 (ARI) | **0.027** | 0 에 붙음 = 거의 무관 |
| PCA 1번 성분 설명력 | **12.9%** | 데이터를 관통하는 축이 없음 |
| 자연스러운 군집 수 | **2개** | 5개가 아니다 |

> **설명변수가 돌봄부담을 5구간으로 가를 만큼의 정보를 담고 있지 않다.**
> 알고리즘을 바꿔도 크게 오르지 않는다.

결정적인 뒷받침 — 같은 모델로 문제만 **"고부담이냐 아니냐"** 로 바꾸면 정확도가
**0.4872 → 0.6985** 로 오른다. **데이터가 자연스럽게 나뉘는 수(2)와 서비스가 실제로 필요한
판정(고부담 여부)이 일치한다.**

확률 보정도 확인했다. 모델이 "55% 확신"이라 말할 때 실제로 55% 맞는지를 10구간으로 나눠
가중 평균한 값(ECE)이다.

| 구분 | ECE | 평균 확신도 | 실제 정확도 |
|---|---|---|---|
| train | **0.0197** | 0.4813 | 0.4862 |
| test | **0.0268** | 0.4851 | 0.4585 |

**보정이 불필요하다.** 로지스틱 회귀는 원래 잘 보정된다. test 에서 확신도가 실제보다
2.7%p 높게 나오지만(약간 낙관적) 실용상 무시할 수준이다. 다만 확신도 0.7 이상 구간은
test 에 8건뿐이라 그 구간의 수치는 신뢰할 수 없다.

## 9. 배포 전 확인할 위험 세 가지

### ① DB 성능 기록 오염 — **2026-09-02 11:37 정정 완료**

`cb_model_version_v1` 의 v1.0.0 행이 **14문항 모델 평가 결과로 덮여 있었다.**

| | 판정 불가율 | macro F1 | 고부담 재현율 |
|---|---|---|---|
| DB 기록 (오염) | **0.0415** | 0.3420 | 0.7669 |
| 실제 v1.0.0 (이 문서) | **0.0249** | 0.3470 | 0.7736 |
| 14문항 v1.1.0 | 0.0420 | | |

기록된 `activated_at` 이 어제 14:48(KST)였는데, 이때는 14문항 모델이 최상위 `models/` 에
올라가 있던 시간대(14:21~15:10)다. 원인은 `record_model_version()` 이 `model_version` 을
키로 `ON DUPLICATE KEY UPDATE` 하기 때문이다 — 평가 시 `MODEL_VERSION` 을 주지 않으면 덮어쓴다.

**정정 방법** — 값을 손으로 고치지 않고 같은 코드 경로로 다시 만들었다.

```bash
MODEL_VERSION=v1.0.0 QSET_VERSION=qs-v1.0.0 python3 ml/train.py evaluate
```

```
DB 현재값  macro F1 0.3416 · 재현율 0.7730 · 판정불가 0.0249   (SC 4항목 전부 PASS)
```

정정 전 값은 `scratchpad/cb_model_version_v1-정정전-백업.json` 에 남겼다.

**남은 것** — 14문항(v1.1.0) 평가 결과가 이 정정으로 DB에서 사라졌다. 실험 이력으로 남기려면
`MODEL_VERSION=v1.1.0` 으로 별도 행을 기록해야 한다(모델을 v1.1.0 으로 바꿔 끼워야 하므로
배포 중에는 하지 않는 편이 좋다). **재발 방지는 학습 라이브러리 설계의 `record --model-version`
필수 인자로 처리한다**(`docs/HG_학습-라이브러리-설계.md` 4.6).

### ② 프론트엔드가 개발 서버로 운영되고 있다

`p3.sumzip.com` 의 프론트는 빌드 산출물이 아니라 **`vite dev`(포트 9503)** 다. 소스를 고치면
즉시 배포되는 반면 백엔드는 수동 재기동이 필요하다. **이 비대칭 때문에 오늘 오전 판정 불가
화면이 통째로 사라지는 사고가 났다** — 프론트만 새 코드로 넘어가고 백엔드는 전날 프로세스로
남아 응답 필드 이름이 어긋났다.

배포 전에 `npm run build` + 정적 서빙으로 바꾸는 것을 권한다.

### ③ 판정 불가 임계값을 런타임이 설정에서 읽지 않는다

`diagnosisService` 는 임계값을 `models/uncertainty_v1.json` 에서 직접 읽는다.
DB 의 `undecidable.thresholds` 는 기동 시 존재만 확인하고 **판정에 쓰이지 않는다.**
FR-009c("코드 수정 없이 조정 가능")가 성립하지 않는다.

지금은 두 값이 일치하므로(0.32391675903458894 / -2.4342723737738483) **동작상 문제는 없다.**
규정 위반과, 설정을 고쳐도 반영되지 않는다는 함정이 남는다.

### 그 밖에

- DB `cb_question_v1` 에 14문항 집합(`qs-v1.1.0`, 15행)이 잔재로 남아 있다. 모델이
  `qs-v1.0.0` 만 참조하므로 서비스 영향은 없다
- `models/v1.1.0`·`v1.2.0` 에는 `parity_v1.json` 이 없다 — **릴리스 게이트를 통과한 적이 없는
  실험용 모델**이다. 배포 후보로 오해하지 말 것
- 버전 번호가 7문항 → 14문항을 minor(`v1.1.0`)로 올렸다. 입력 계약이 바뀌는 변경이므로
  major 가 맞다. 문항 집합 버전이 갈려 있어 실제 혼선은 막히지만 이름이 오해를 부른다

## 10. 결론

**배포해도 된다.** 성공 기준 SC-004·SC-005·SC-016 을 모두 충족하고, 과적합이 거의 없으며,
오차가 인접 구간에 몰려 있어 안내 목적에서 위험한 방향으로 틀리지 않는다.

**단, 이렇게 말해야 한다.**

- "5개 구간을 정확히 맞히는 서비스"가 아니다. 정확도 48.7% 는 그렇게 쓸 수 없는 수치다
- **"고부담을 놓치지 않는 서비스"** 다. 실제 고부담자의 77.4% 를 잡아내고, 못 잡은 경우도
  대부분 인접 구간으로 분류된다
- 정확도가 낮은 이유는 데이터에 5구간 구조가 없기 때문이고, **그것을 군집화로 입증해 두었다**

배포 전 처리 순서로는 **① DB 성능 기록 정정**(발표에 직접 영향) → **② 프론트 빌드 배포 전환**
(사고 재발 방지) → ③ 임계값 설정 연결(규정) 을 권한다.
