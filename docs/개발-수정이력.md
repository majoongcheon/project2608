### 2-1. 외부 검토 반영 — 명세 13건 수정 (9/1)

**접근성 결정 번복** — 원래 "실 서비스 계획 없음"을 이유로 접근성을 전면 제외했으나,

**기본 사용성 4가지(FR-039~042)를 범위에 유지**하기로 바꿨다. 인증 취득이 아니라
결과 오독 방지가 목적이다.

### 2-2. 계획 단계 — DB 실측으로 검증 (9/1)

계획을 추정으로 세우지 않고 **DB를 직접 조회해 spec.md의 모든 수치를 대조**했다. 전부 일치했고,
예상하지 못한 자산 두 가지를 발견해 계획에 반영했다.

- **`cv_fold` 가 train 2,398건에 5-fold로 이미 배정되어 있었다**(483/481/478/478/478).
  덕분에 문항 선별과 임계값 보정이 같은 분할 위에서 재현된다.
- **`v_cb_tree_v1`·`v_cb_linear_v1` 두 뷰가 준비되어 있었다.** 결측 처리가 정반대(NULL 유지 vs

  이 발견이 "계열을 사전에 정하지 않고 벤치마크로 고른다"는 R-1 결정의 근거가 됐다.

## 3. 발표에서 다룰 만한 사례 5선

### 3-1. 명세 안의 논리 모순 — FR-031 ↔ FR-033

> **FR-031** 시스템은 제출된 진단 응답을 학습용 데이터로 **저장해야 한다**.
> **FR-033** 동의하지 않으면 응답은 학습용으로 **저장되지 않는다**.

두 문장이 정면으로 충돌한다. 사람이 읽으면 "당연히 동의한 경우만"이라고 보정해 읽히지만,
**명세로서는 어느 쪽을 구현해도 다른 쪽을 위반**한다.

→ FR-031을 "**학습·검증 이용에 동의한 경우에 한하여** 저장할 수 있어야 한다"로 수정.

**시사점**: 개별 요구사항이 각각 타당해도 조합하면 모순일 수 있다. 외부 검토가 이를 잡아냈다.

### 3-2. 성능 미달을 "배제 규칙을 되돌리지 않고" 해결한 과정

첫 학습에서 **고부담 재현율 0.678** — SC-005의 하한 0.70에 미달했다.

원인은 `class_weight='balanced'` 였다. 표본 61건뿐인 5단계(부담 없음)를 끌어올리려다
**다수 구간인 고부담(1~2단계, 54.3%)을 억눌렀다.**

가장 쉬운 해결책은 Data Leakage 방지로 배제한 6개 변수를 되살리는 것이었다. 그중
`I14 보호자 생활만족도`는 단독 설명력 **19.06%** 로 남은 변수 1위(8.23%)의 2.3배다.
넣으면 성능은 확실히 오른다.

**그러나 spec Risks 가 이 경우를 미리 금지해 두었다** — "성능을 회복하려 배제 규칙을 되돌리지
않고 문항 조합 재선별 또는 성공 기준 재조정으로 대응한다". 보호자 생활만족도로 보호자
돌봄부담을 예측하는 것은 동어반복이라 진단 도구의 존재 이유가 사라지기 때문이다.

→ 대신 **결정 가중치**를 도입했다. 고부담(1·2단계) 확률에 1.1배를 곱해 판정한다.
재현율 0.7122 → **0.7636**, macro F1도 0.3153 → 0.3180으로 함께 올랐다.
가중치는 코드가 아니라 학습으로 도출해 아티팩트에 실었다(원칙 I·IV).

**시사점**: 명세가 "이럴 때 이렇게 하지 마라"를 미리 적어 두면, 압박 상황에서 잘못된 지름길을 막는다.

### 3-3. 교차검증을 믿었다가 test에서 실패한 것

후진 제거로 문항을 줄이는데, CV 기준 최소 k를 그대로 골랐더니 **k=6**이 나왔다.
CV에서는 F1 손실 0.0229로 기준(0.03) 안이었다.

그런데 **test에서는 손실 0.0319 — SC-004 실패.** CV 잡음에 선택이 과적합된 것이다.

두 가지를 고쳤다.

1. **마진 도입** — CV에서 `0.03 - 0.01` 을 기준으로 삼아 test 변동을 흡수
2. **동일 조건 비교** — 기준 모델(38변수)도 같은 test에서 평가.
   그전에는 *선택 모델의 test 성능*을 *기준 모델의 CV 성능*과 비교하고 있었다(추정 방식이 달라 왜곡)

→ k=7로 확정, 4개 게이트 전부 통과.

**시사점**: "최소값 선택"은 그 자체로 선택 편향이다. 그리고 비교는 같은 조건에서 해야 한다.

### 3-4. 502의 원인은 포트가 아니었다

`p3.sumzip.com` 이 502를 반환했다. nginx 설정을 보니 `proxy_pass https://192.168.0.19:9503`.
처음에는 "포트가 9513인데 9503을 가리켜서"라고 판단했다.

그런데 **팀 배정 포트가 9503으로 확인되어 포트를 맞춰도 502가 그대로였다.**
nginx 에러 로그가 답을 줬다.

```
SSL_do_handshake() failed (SSL: error:0A00010B:SSL routines::wrong version number)
while SSL handshaking to upstream, upstream: "https://192.168.0.19:9503/"
```

`wrong version number` — **평문 HTTP 서버에 TLS로 말을 건 것**이다. 스킴이 `https` 였다.
직접 재현해 확인했다: `https://192.168.0.19:9503` 실패, `http://192.168.0.19:9503` 200.

**시사점**: 추론으로 원인을 단정하지 말고 로그를 봐야 한다. 그리고 재현 가능한지 확인해야 한다.

### 3-5. 지도가 애초에 마커를 그릴 수 없었다

팀 요청(JSG-01)으로 지도를 Kakao SDK → Leaflet + OpenStreetMap 으로 교체하다가 발견했다.

`MapView` 는 `if (f.lat == null || f.lng == null) continue;` 로 좌표 없는 항목을 건너뛰는데,
**`/facilities` 응답에 `lat`·`lng` 가 아예 없었다.** 즉 카카오 키가 있었어도 **빈 지도**만 나왔다.

키가 없어 항상 목록으로 폴백되는 바람에 그때까지 드러나지 않았다.

**시사점**: 폴백이 잘 동작하면 그 뒤의 결함이 가려진다. 폴백 경로만 검증하고 본 경로를
검증하지 않으면 이런 것을 놓친다.
