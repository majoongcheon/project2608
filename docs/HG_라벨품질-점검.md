## 2. 라벨은 상식적인 방향으로 붙는다

`care_burden` 과 각 변수의 스피어만 상관. **1이 최고부담인 역방향 척도**라 부호를 읽을 때 주의한다.

| 변수 | r | p | n |
|---|---|---|---|
| `help_needed_hours` | **+0.442** | 2.5e-115 | 2,398 |
| `understands_work_meaning` | **−0.429** | 7.7e-108 | 2,398 |
| `can_work_standard_job` | −0.396 | 1.2e-90 | 2,398 |
| `overall_health` | +0.270 | 2.1e-41 | 2,398 |
| `family_support_for_employment` | +0.247 | 1.1e-34 | 2,395 |
| `is_employed` | −0.247 | 1.1e-34 | 2,398 |
| `daily_routine_satisfaction` | +0.241 | 5.4e-33 | 2,395 |
| `job_ability_mobility` | +0.228 | 9.9e-30 | 2,398 |

`|r| ≥ 0.20` 인 변수가 38개 중 8개, `|r| ≥ 0.10` 이 18개다.

### 2.1 방향을 코드북과 대조했다

배포 문항 4개는 선택지 문구를 직접 확인해 방향이 맞는지 봤다(`GET /api/v1/questions`).

| 변수 | 선택지 방향 | r | 읽으면 | 맞나 |
|---|---|---|---|---|
| `help_needed_hours` | 1=하루 12시간 이상 … 5=필요 없음 | +0.442 | 도움이 많이 필요할수록 부담이 크다 | ✓ |
| `understands_work_meaning` | 1=잘 이해 … 4=전혀 이해 못함 | −0.429 | 이해하지 못할수록 부담이 크다 | ✓ |
| `family_support_for_employment` | 1=전혀 지지 안 함 … 5=매우 지지 | +0.247 | 가족 지지가 낮을수록 부담이 크다 | ✓ |
| `daily_routine_satisfaction` | 1=매우 싫어한다 … 5=매우 좋아한다 | +0.241 | 당사자가 일과를 싫어할수록 부담이 크다 | ✓ |

**네 개 다 상식과 같은 방향이다.** 라벨이 무작위로 붙었다면 이런 게 나올 수 없다.
"라벨이 엉망이다" 라는 가설은 이 지점에서 약해진다.

## 3. 그런데 같은 답을 낸 사람끼리 갈린다

### 3.1 모델이 쓰는 7문항 시야

```
서로 다른 응답 조합            1,156개
2명 이상인 조합                 326개
  ├ 라벨이 갈린 조합            261개 = 80.1%
  └ 고부담/아님 에서도 갈림      205개 = 62.9%
갈린 폭   1칸 111개 · 2칸 95개 · 3칸 48개 · 4칸 7개
천장 정확도   5구간 72.3%  ·  고부담 2분류 85.0%
```

**4칸 갈린 조합이 7개** 있다. 7문항에 똑같이 답했는데 한 사람은 최고부담군,
다른 사람은 부담 없음이다.

### 3.2 전체 38변수 시야

```
서로 다른 응답 조합            2,398개
2명 이상인 조합                  0개
```

**중복이 한 건도 없다. 2,398명 전원이 유일한 응답 조합이다.**

## 4. 앞선 설명 정정 — "천장 70.6%" 가 뜻하는 것

지금까지 문서들(`HG_모델-개선-검토.md`, `HG_서열모델-기록.md`)에서 근거로 삼은
"천장 70.6%(train 기준 72.3%)" 는 **7문항 시야의 천장**이다.
38변수로 보면 중복이 0건이라 이 방식으로는 천장을 아예 셀 수 없다.

즉 그 숫자는 **"라벨이 나쁘다" 의 증거가 아니다.** 다음 둘이 아직 안 갈린 상태였다.

```
(A) 라벨이 흔들린다          같은 사람 상황에 매겨진 값이 일관되지 않다
(B) 7문항이 부족하다         라벨은 멀쩡한데 7개로는 못 본다
```

5장이 이걸 가른다.

## 5. 정보량 비교 — 변수를 늘리면 오르는가

같은 5-fold, 같은 결정 가중치로 변수 개수만 바꿨다.

| | macro F1 | 고부담 재현율 | 정확도 | 고부담 2분류 | 두 칸 이상 |
|---|---|---|---|---|---|
| **7문항 (배포본)** | **0.3364** | 0.7844 | **46.3%** | **69.4%** | 9.8% |
| 38변수 로지스틱 | 0.3141 | 0.7322 | 41.3% | 65.5% | 12.5% |
| 38변수 랜덤포레스트 | 0.2825 | 0.7928 | 45.8% | 69.1% | 8.8% |

**변수를 5배 넣어도 오르지 않는다. 오히려 내려간다.**

로지스틱이 내려간 것은 원-핫 열이 늘어난 과적합으로 설명할 수 있지만,
그 걱정이 없는 랜덤포레스트도 정확도 45.8% · 고부담 2분류 69.1% 로 7문항과 같은 자리다.
**나머지 31개 변수에 더 들어 있는 정보가 사실상 없다.**

→ 가설 (B) "문항이 부족하다" 는 힘을 잃는다.
→ 남는 설명은 **이 설문이 담은 정보와 부담 라벨 사이의 관계 자체가 약하다** 쪽이다.

## 6. 라벨 분포 — 척도 사용 습관

| 내부 라벨 | 표시 명칭 | train 건수 | 비율 |
|---|---|---|---|
| 1 | 최고부담군 | 371 | 15.5% |
| 2 | 고부담군 | 932 | **38.9%** |
| 3 | 중간부담군 | 732 | 30.5% |
| 4 | 저부담군 | 302 | 12.6% |
| 5 | 부담 없음 | 61 | **2.5%** |

가운데(2~3번군)에 69.4% 가 몰리고 5번군은 61명뿐이다.
5점 척도에서 양 끝을 잘 안 쓰는 **중심화 경향**으로 보인다.
이건 응답자의 습관이라 알고리즘으로는 못 고친다.
"구간을 5개로 나눈 것이 애초에 무리였는가" 를 검토할 근거가 된다.

## 7. 그래서 지금 서 있는 자리

```
라벨에 신호는 있다        (2장 — 상식 방향으로 최대 r=0.442)
그런데 같은 답에서 갈린다   (3장 — 62.9% 가 고부담 여부에서조차 갈림)
변수를 늘려도 안 오른다     (5장 — 38변수도 7문항과 같은 자리)
```

세 개를 합치면 **"라벨이 완전히 망가진 것도 아니고, 문항이 모자란 것도 아니다.
이 설문 도구로 설명되는 부담의 몫이 원래 작다"** 가 된다.

이는 지금까지의 실험 셋(정규화 튜닝 · 14문항 · 서열 모델)이 전부 실패한 것과 앞뒤가 맞는다.
**모델을 만져서 넘을 벽이 아니다.** 다만 그 원인이 "라벨 품질" 하나로 좁혀지지는 않았다.

## 8. 안 한 것 — 했다고 오해하지 말 것

아래 넷은 **이번에 하지 않았다.** 하려면 별도로 진행해야 한다.

| # | 검사 | 필요한 것 | 무엇을 가릴 수 있나 |
|---|---|---|---|
| ① | **제외 6변수를 잣대로 쓰는 수렴 타당도** | DB 읽기 | 부담이 크다는 사람이 삶의 만족도도 낮고 돌봄 공백도 큰가. 라벨 검증의 가장 직접적인 방법 |
| ② | 모순 응답 탐지 | 스냅샷 | 논리적으로 안 맞는 응답 쌍의 비율. 높으면 라벨이 아니라 **수집 과정** 문제 |
| ③ | 수집 배치·조사원 효과 | DB 읽기 | 배치별로 라벨 분포가 다르면 사람이 아니라 절차가 만든 차이 |
| ④ | 설문지 원본의 I13 문항 문구 검토 | 사람이 읽어야 함 | 문항이 애매하거나 바람직한 답이 뻔하면 자기보고가 흔들린다 |

①에 대해서는 **FR-004b 해석이 걸린다.** 규칙은 "입력·문항 어디에도 쓰지 않는다" 이고
라벨 검증용 분석은 입력도 문항도 아니지만, 결과가 모델로 새지 않도록
별도 스크립트로만 돌리고 파이프라인은 건드리지 않는 전제가 필요하다. **팀 확인 사항이다.**

### 아예 불가능한 것

**재측정 신뢰도(test-retest)는 낼 수 없다.** 같은 사람이 두 번 답한 데이터가 원자료에 없다.
"이 사람이 다음 주에 다시 답하면 같은 값이 나오는가" 는 라벨 품질 검증의 정공법인데,
이 데이터로는 영영 못 잰다. 위 ①~④ 는 전부 그 대용품이다.
