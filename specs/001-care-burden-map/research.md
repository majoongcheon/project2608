## R-1. 모델 계열 — 트리 앙상블을 주 후보로, 선형 계열을 대조군으로

**결정**: 두 계열을 같은 5-fold로 벤치마크하고 SC-004·SC-005로 선택한다. 사전에 하나를 고르지 않는다.

| 계열 | 입력 뷰 | 후보 | 결측 처리 |
|---|---|---|---|
| 트리 앙상블 (주 후보) | `v_cb_tree_v1` | LightGBM · RandomForest · HistGradientBoosting | NULL을 분기에서 네이티브 처리 |
| 선형/순서형 (대조군) | `v_cb_linear_v1` | Multinomial Logistic · Ordinal Logistic(비례오즈) | `-1` 대체 + `*_isna` 플래그 |

**근거**

1. **결측이 정보다.** 38개 중 14개에 결측이 있고, 88.1% / 30.2% / 69.8% 같은 값으로 뭉친다.
   이는 누락이 아니라 분기 문항의 "해당 없음"이며(FR-004d), 트리 계열은 이 구조를 별도 인코딩
   없이 분기로 흡수한다. `v_cb_tree_v1`이 NULL을 원형 유지하는 이유가 여기 있다.
2. **범주형이 지배적이다.** continuous는 4개뿐이고 nominal 9개(`last_job_quit_reason` 15레벨,
   `has_chronic_disease` 18레벨)는 순서가 없다. 선형 모델은 이를 원-핫으로 펼쳐야 하고
   3,000건 규모에서 차원이 빠르게 불리해진다.
3. **그럼에도 대조군을 버리지 않는 이유** — 순서형 로지스틱은 target이 1~5 순서 척도라는 구조를
   직접 활용하고, 계수 자체가 설명이 되어 FR-011의 자연어 변환이 단순해진다. 성능 차가 SC-004
   허용 범위 안이면 설명가능성 우위로 선택할 수 있다.

**기각한 대안**

- *신경망 계열* — 3,000건 × 38변수 규모에서 트리 앙상블을 이길 근거가 없고, FR-011의 개별 기여도
  산출이 복잡해지며, 원칙 IV(재현성)를 위해 시드·연산 순서까지 고정해야 하는 부담이 크다.
- *처음부터 트리로 확정* — 원칙 I의 "단변량 지표만으로 취사선택 금지"와 같은 취지에서, 계열 선택도
  실측으로 결정한다. 두 뷰가 이미 준비된 이상 대조 비용은 낮다.

## R-2. 런타임 추론 — 학습은 Python, 추론은 TypeScript 네이티브

**결정**: 학습·선별·보정은 오프라인 Python 파이프라인(`ml/`)에서 수행해 **버전이 부여된 JSON 아티팩트**를
내보내고, 운영 중 추론은 백엔드(Node 20 + Express + TS)가 그 JSON을 읽어 **TypeScript로 직접 계산**한다.
**런타임에 Python 프로세스는 존재하지 않는다.**

```text
[오프라인 · 학습 시점]                        [런타임 · 매 제출]
ml/  (Python)                                backend/src/inference/  (TypeScript)
  ├ 데이터 적재 (v_cb_tree_v1)                  ├ model_v1.json 로드 (기동 시 1회)
  ├ 문항 선별 (FR-004c)                         ├ 트리 순회 → 구간 확률
  ├ 학습 · 하이퍼파라미터 탐색                    ├ TreeSHAP → 개별 기여도 (FR-011a)
  ├ 판정 불가 기준 보정 (FR-009b)                ├ 판정 불가 판단 (FR-009a)
  └ export → models/model_v1.json              └ 결과 반환 (FR-026a: p95 3초)
```

**근거**

1. **원칙 V(컨테이너 없는 전개, NON-NEGOTIABLE)를 지키는 유일하게 단순한 방법이다.** Python 추론
   서비스를 두면 별도 프로세스 관리·포트·프로세스 감독이 필요해지고, 그 순간 "컨테이너 없이
   전개한다"는 요구가 오히려 복잡해진다. 아티팩트 하나만 넘기면 배포 단위가 Node 하나로 끝난다.
2. **스택 제약을 만족한다.** 서비스 구성 요소는 Vue/Node/MariaDB를 벗어나지 않는다. Python은
   배포되지 않는 분석 도구이며, 이미 저장소의 `notebooks/`가 같은 지위에 있다.
3. **성능이 문제되지 않는다.** 트리 수백 개 순회는 TS에서 밀리초 단위다. FR-026a의 3초는 기여도
   산출까지 포함한 값인데, 실제 병목은 모델이 아니라 네트워크와 DB 조회다.
4. **원칙 IV(재현성)에 유리하다.** 부동소수 연산 순서가 코드에 고정되므로 동일 입력 → 동일 출력이
   구조적으로 보장된다. 파이썬-노드 간 직렬화 경계가 없어 버전 간 미세 차이도 생기지 않는다.

**기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| Python FastAPI 추론 서비스 | 스택 제약 위반. 프로세스 2개 운영은 원칙 V의 "폴더 안 코드 전개" 취지에 역행 |
| ONNX Runtime for Node | 네이티브 바이너리 의존이 생기고, TreeSHAP 기여도를 ONNX 그래프로 얻기 어렵다 |
| 학습까지 TS로 | LightGBM·SHAP·교차검증 도구가 Python 생태계에 있다. 오프라인 단계까지 제약할 이유가 없다 |
| 판정 결과를 사전 계산해 DB 적재 | 38변수 조합은 조합폭발이라 불가능 |

**남는 위험** — TS 추론기와 Python 학습기가 같은 결과를 내는지 보장해야 한다.
완화책: export 직후 **train+test 3,000건 전량을 양쪽에 통과시켜 클래스 확률이 1e-9 이내로
일치하는지 검증하는 패리티 테스트**를 릴리스 게이트로 둔다(quickstart.md 참조).

## R-3. 기여 요인 산출 — TreeSHAP을 TypeScript로 구현

**결정**: 트리 계열이 선택되면 **TreeSHAP(path-dependent)** 을 TS로 구현한다.
선형 계열이 선택되면 기여도는 `계수 × (값 − 기준값)`으로 직접 산출한다.

**근거**

- FR-011a는 "제출된 응답에 대한 개별 예측 기여도"를 요구하고, 원칙 II는 구간별 고정 문구를 금지한다.
  SHAP은 기여도의 합이 예측값과 정확히 일치하는(local accuracy) 유일한 표준 기법이라,
  "왜 이 판정인가"를 산술적으로 닫힌 형태로 설명할 수 있다.
- 알고리즘이 공개·확정되어 있어 TS 이식이 가능하다(Lundberg 2018, 트리당 O(TLD²)).
- 배경 분포가 필요 없는 path-dependent 방식을 쓰면 런타임에 학습 데이터를 들고 있지 않아도 되어
  원칙 III(최소 수집)와도 맞는다.

**기각한 대안**

- *Saabas 기여도* — 구현은 훨씬 간단하나 분기 순서에 따라 값이 치우쳐, 같은 응답에 대해 요인 순위가
  뒤바뀔 수 있다. **다만 TreeSHAP 이식이 일정상 위험해지면 이것을 폴백으로 둔다**(그 경우
  기여도를 순위로만 쓰고 크기를 화면에 표기하지 않는다).
- *Permutation importance* — 전역 중요도라 개별 응답 설명이 불가능하다. FR-011a 요건 미달.
- *LIME* — 국소 대리모델이라 재현성이 확률적이다. 원칙 IV 위반.

**FR-011-1 연계** — 검토 반영으로 신설된 "기여도 임계값 미만 요인 구분 표시"는 SHAP 절댓값을
기준으로 판단한다. 임계값은 학습 시 검증셋 SHAP 분포의 하위 분위로 도출해 설정에 기록한다.

**FR-011 자연어 변환의 함정** — 노트북 5장이 실측한 `secondary_caregiver_type` 역설
(보조 돌봄제공자가 **있는** 쪽의 고부담 비율이 +3.8%p 높다)은 역인과다. SHAP 기여도를 그대로
문장으로 옮기면 "보조 돌봄제공자가 있어서 부담이 크다"는 **인과 오독**을 만든다.
→ 문항별 자연어 템플릿을 사람이 검수하고, 인과 표현 대신 **동반 관찰 표현**을 쓴다.
(예: "보조 돌봄제공자가 있는 가구에서 이 응답 조합이 더 자주 나타납니다")

## R-4. 최소 문항 집합 도출 (FR-004c) — 5-fold 순차 후진 제거

**결정**: `cv_fold`에 이미 배정된 5-fold로 **재귀적 특징 제거(RFE)** 를 돌리고,
SC-004·SC-005를 동시에 만족하는 **가장 작은** 집합을 채택한다. test 602건은 사용하지 않는다.

```text
1. 기준 모델   : 38변수 전체 · 5-fold CV → macro F1 = B_f1, 고부담 재현율 = B_rec (기준선 확정)
2. 후진 제거   : 매 회 SHAP 전역 중요도 최하위 변수 1개 제거 → 5-fold 재학습 → 지표 기록
3. 정지 조건   : (B_f1 − f1) ≤ 0.03  AND  (B_rec − rec) ≤ 0.05  AND  rec ≥ 0.70
4. 채택        : 정지 조건을 만족하는 최소 변수 수 k. 동률이면 결측률이 낮은 조합을 택한다
5. 기록        : k, 채택 변수, 탈락 순서, 각 단계 지표를 models/selection_v1.json 에 남긴다
```

**근거**

- 원칙 I이 "단변량 지표만으로 취사선택 금지"를 못박고, 노트북 3장도 같은 결론을 명시했다
  ("이 순위가 아니라 38개 전체 모델 대비 성능 손실 기준으로 정한다"). MI 순위는 **참고 자료**일 뿐이다.
- 후진 제거는 변수 간 중복을 반영한다. 예컨대 `is_employed`(MI 2.32)와 `employment_status`(2.54)는
  상당 부분 같은 정보이므로, 단변량 순위로는 둘 다 살아남지만 후진 제거는 하나를 떨군다.
- fold가 DB에 고정되어 있어 재현성이 보장된다(원칙 IV). 매번 다시 나누면 k가 흔들린다.

**결측률이 낮은 조합을 선호하는 이유** — `wanted_to_stay_at_last_job`류(결측 88.1%)는 대다수
보호자에게 "해당사항 없음"만 받는 문항이라, 성능 기여가 같다면 실제 설문에서 정보량이 낮다.

**기각한 대안**

- *MI 상위 k개 절단* — 원칙 I 위반. 중복을 반영하지 못한다.
- *전진 선택* — 초기 선택이 이후를 강하게 구속하고, 상호작용으로만 기여하는 변수를 놓친다.
- *L1 정규화 자동 선별* — 선형 계열에서만 쓸 수 있어 계열 선택 전에는 적용할 수 없다.

**예상 결과의 불확실성** — 노트북은 MI 1% 이상이 21개, 미만이 17개임을 보였다. k가 20 근처로
수렴하면 "경량 진단" 성격이 유지되지만, 30을 넘으면 제품 성격이 약해진다(spec Risks에 기록됨).
**k는 이 단계의 산출물이며 지금 값을 못박지 않는다**(원칙 I).

## R-5. 클래스 불균형 — 클래스 가중치, 리샘플링 없음

**결정**: 손실 함수에 `class_weight='balanced'` 계열의 가중치를 적용한다. 오버/언더샘플링은 쓰지 않는다.

**근거**

- 5단계(부담 없음)는 train 61건뿐이고 macro F1은 이 구간을 다른 구간과 동등하게 평균하므로,
  가중치 없이는 5단계가 사실상 예측되지 않아 SC-004가 구조적으로 불리해진다.
- SMOTE류 합성은 범주형·결측이 섞인 이 데이터에서 의미 없는 조합을 만든다
  (예: 과거 취업 경험이 "없음"인데 퇴사 이유가 채워진 행).
- 언더샘플링은 3,000건 규모에서 정보 손실이 크다.

**주의** — 가중치는 확률 보정을 왜곡한다. FR-009b의 판정 불가 기준은 보정된 확률 위에서 정해져야
하므로, **가중치 학습 → 확률 보정(isotonic/Platt) → 임계값 산출** 순서를 지킨다.

## R-6. 판정 불가 기준 (FR-009a·FR-009b) — 두 신호의 결합, CV로 보정

**결정**: **(1) 예측 확신도 부족**과 **(2) 학습 분포에서 드문 응답 조합** 두 신호를 결합한다.
임계값은 train 5-fold로 보정하고, `models/uncertainty_v1.json`에 기록한다.

| 신호 | 지표 | 뜻 |
|---|---|---|
| 확신도 | 보정된 최대 클래스 확률 `max p(y|x)` | 모델이 어느 구간도 자신 있게 고르지 못함 |
| 희소성 | 선택 문항 조합의 학습 데이터 내 근방 밀도 | 학습 데이터가 뒷받침하지 못하는 응답 조합 |

```text
판정 불가  ⟸  max p(y|x) < τ_conf   OR   density(x) < τ_dens
```

**보정 절차 (SC-016을 만족시키는 방향으로)**

1. 5-fold 예측을 모아 각 응답의 `max p`와 밀도를 계산한다.
2. τ를 격자 탐색하며 두 조건을 동시에 확인한다.
   - **판정 불가 집단의 오분류율 > 판정 집단의 오분류율** (SC-016 전반부, FR-009b의 검증 요건)
   - **판정 불가 비율 ≤ 10%** (SC-016 후반부)
3. 두 조건을 만족하는 조합 중 판정 불가 비율이 가장 낮은 τ를 채택한다.
4. τ는 코드가 아니라 설정으로 나간다(FR-009c, 원칙 IV).

**근거** — 확신도만 쓰면 학습 데이터가 아예 없는 영역에서도 모델이 근거 없이 확신할 수 있다.
밀도만 쓰면 흔한 조합인데 구간 경계에 걸린 응답을 놓친다. 두 실패 양상이 다르므로 OR로 묶는다.

**기각한 대안**

- *고정 임계값(예: max p < 0.4)* — 원칙 I의 "근거 없는 추정치 고정 금지" 위반. spec FR-009b도
  사전 고정을 명시적으로 금지한다.
- *컨포멀 예측* — 이론적으로 우수하나 집합 예측(여러 구간 동시 반환)이라 "5구간 중 하나 또는
  판정 불가"라는 FR-009의 출력 형태와 맞지 않는다. 다음 버전 후보로만 기록한다.

## R-7. 지도 서비스 — Leaflet + OpenStreetMap (2026-09-01 번복)

> **이 결정은 한 번 뒤집혔다.** 최초에는 Kakao Maps JS SDK 를 택했으나, 팀 검토(JSG-01)에서
> **발급 키 없이 동작해야 한다**는 요구가 나와 Leaflet + OpenStreetMap 으로 교체했다.
> 아래에 원래 판단과 번복 근거를 모두 남긴다.

**최종 결정**: **Leaflet + OpenStreetMap 타일**. 발급 키가 필요 없다.
거리 계산은 지도 라이브러리에 의존하지 않고 **백엔드가 Haversine 으로 직접 계산**한다(FR-021-1).
중심좌표는 **기준 위치(현재 위치 또는 선택 지역 대표 좌표)** 이며 마커 평균이 아니다.

**번복 근거**

1. **키 없이 동작한다.** 시연·인수인계 때 `.env.local` 설정 없이 지도가 바로 뜬다.
   키 관리가 사라지는 것이 이 프로젝트 규모에서는 실질적 이점이다.
2. **원래 기각 사유가 이 프로젝트에는 해당하지 않는다.** 아래 기각표는 Leaflet+OSM 을
   "국내 상세 주소·건물 정보 부족"으로 떨궜는데, **기관 좌표 1,283건이 이미 DB 에 확보되어
   있어(결측 0건) 지오코딩도 주소 검색도 필요 없다.** 지도의 역할이 "이미 아는 좌표에 마커를
   찍는 것"뿐이라 OSM 타일로 충분하다.
3. **FR-018 길찾기는 영향이 없다.** 외부 지도 서비스의 검색 링크를 여는 방식이라 SDK 를
   걷어내도 그대로 동작한다.
4. 여전히 **클라이언트 라이브러리라 서버 구성 요소가 늘지 않는다** — 원칙 V 와 스택 제약에 무관하다.

**남는 위험** — OSM 타일 서버는 외부 CDN 이다. 폐쇄망·오프라인 시연에서는 타일을 받지 못한다.
이 경우 `tileerror` 를 잡아 목록으로 폴백하며, 데이터 경로가 지도와 분리되어 있어 목록은 그대로 동작한다.

## R-9. 거리 계산과 정렬 — 백엔드 Haversine + 사각 범위 선필터

**결정**: FR-021-1이 직선거리(Haversine)를 확정했다. 구현은 **경계 상자로 후보를 좁힌 뒤
Haversine으로 정렬**하는 2단계로 한다.

```sql
-- 1단계: 인덱스 활용 가능한 사각 범위로 후보 축소 (반경 r km → 위경도 델타)
WHERE lat BETWEEN :lat - :dlat AND :lat + :dlat
  AND lng BETWEEN :lng - :dlng AND :lng + :dlng
-- 2단계: 후보에 대해서만 Haversine 계산 후 정렬 · 상위 N
```

**근거** — Haversine을 1,283행 전체에 걸면 인덱스를 못 쓴다. 사각 범위는 `(lat, lng)` 인덱스를
타므로 후보가 수십 건으로 줄고, 그 위의 삼각함수 비용은 무시할 수 있다. 사각 범위는 원보다 넓어
후보를 놓치지 않는다(과대 포함은 2단계에서 걸러진다).

**반경이 비면** FR-021f/FR-020에 따라 범위를 단계적으로 확대한다(기본 10 → 20 → 50km, 설정값).

## R-10. 세션·중복 제출·개인정보 (FR-008-1, FR-029, FR-036a~c)

**결정**

| 항목 | 구현 |
|---|---|
| 진행 상태(FR-008-1) | 브라우저 `localStorage`. Pinia 스토어를 직렬화. 서버 전송 없음 |
| 만료(FR-008-2) | 저장 시각 타임스탬프 동봉. 로드 시 24시간 경과·제출 완료·"새로 시작"이면 폐기 |
| 별명(FR-002d) | `sessionStorage`. 탭을 닫으면 사라져 FR-002d의 "세션 안에서만"과 일치 |
| 세션 식별자(FR-029) | 요청 시 서버가 발급하는 UUIDv4. 이용자와 연결 가능한 어떤 값도 입력에 넣지 않는다 |
| 제출자 해시(FR-036) | `SHA-256(IP + 비공개 솔트)`. 원본 IP는 요청 처리 중 메모리에만 존재하고 로깅 금지 |
| 솔트 교체(FR-037) | 분기 1회. 설정 테이블에 `active_from`을 두고 교체 이력을 남긴다 |
| 중복 억제(FR-036c) | 해시 + 세션 + 시간창 3중. **자동 차단하지 않고 플래그만 기록**(FR-036a) |

**별명을 `localStorage`가 아닌 `sessionStorage`에 두는 이유** — FR-002d는 "진행 중인 세션 안에서만
유지"를 요구하고, 검토 6번에서 재접속 시 별명 미복구를 **의도된 동작**으로 확정했다.
두 저장소를 나누면 이 차이가 코드에 그대로 드러난다.

**로깅 주의** — Express 기본 액세스 로그와 리버스 프록시(Nginx) 로그가 IP를 남긴다.
FR-028·원칙 III를 지키려면 **애플리케이션 로그의 IP 필드를 명시적으로 비활성화**하고
Nginx 쪽 `log_format`에서도 제거해야 한다. 이건 코드가 아니라 배포 설정이므로 별도 작업으로 남긴다.
