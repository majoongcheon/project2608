# 돌봄부담 진단·복지연계 서비스 Constitution

## Core Principles

### I. 근거 기반 판정 (NON-NEGOTIABLE)

판정 결과에 영향을 주는 모든 값 — 문항 집합, 판정 임계값, 변수 배제 규칙, 성능 목표 — 은
실측으로 도출하고 그 근거를 문서로 남겨야 한다(MUST).

- 예측 대상(target)과 동일한 설문 블록에 속하거나 동일한 구성개념을 측정하는 변수는
  모델 입력과 설문 문항 어느 쪽으로도 사용해서는 안 된다(MUST NOT). Data Leakage 방지.
- 근거 없는 추정치를 명세에 확정값으로 고정해서는 안 된다(MUST NOT). 값을 정할 수 없다면
  값 대신 **도출 규칙**을 명시하고, 측정 결과로 확정한다.
- 단변량 지표만으로 변수를 취사선택해서는 안 된다(MUST NOT). 변수 간 상호작용과 중복을
  반영하는 방법으로 검증한다.

Rationale: 이 서비스는 복지 자원 배분에 영향을 준다. 근거 없는 숫자가 명세에 박히면
그 숫자가 검증 없이 구현·평가 기준으로 굳어지고, 사후에 되돌리는 비용이 크다.

### II. 설명가능성과 정직한 불확실성

모든 판정에는 그 응답에 대한 개별 근거가 함께 제시되어야 한다(MUST).

- 근거를 제시할 수 없는 입력에 대해서는 판정을 내리지 않고 "판정 불가"를 반환해야 한다(MUST).
  불확실한 판정을 확신처럼 제시하는 것보다 판정하지 않는 편이 낫다.
- 판정 근거를 구간별 고정 문구로 대체해서는 안 된다(MUST NOT).
- 결과는 참고 정보이며 공식 복지 자격 판정이 아님을 명시해야 한다(MUST).
- 내부 라벨값·척도를 이용자에게 그대로 노출해서는 안 된다(MUST NOT). 의미가 담긴 명칭으로
  변환해 제시한다.

Rationale: 보호자와 복지 현장이 결과를 신뢰하려면 "왜 그렇게 판단했는가"에 답할 수 있어야
한다. 근거 없는 판정은 사각지대를 줄이는 대신 잘못된 확신을 만든다.

### III. 최소 수집과 익명성 (NON-NEGOTIABLE)

이용자는 계정 없이 서비스를 이용하며, 시스템은 이용자를 식별할 수 있는 정보를 보유하지
않아야 한다(MUST NOT).

- 개인 식별 정보와 원본 IP 주소를 어떤 저장소에도 보관해서는 안 된다(MUST NOT).
  구분이 필요하면 솔트를 결합한 단방향 해시를 사용하고, 솔트를 정기 교체한다.
- 저장 항목은 명세에 열거된 범위를 넘어서는 안 되며(MUST NOT), 각 저장소는 이용 목적과
  보존 기간을 명시하고 경과분을 자동 파기해야 한다(MUST).
- 수집 목적을 확대할 때는 사전 고지와 동의를 받아야 하며(MUST), 동의하지 않아도 핵심 기능을
  온전히 이용할 수 있어야 한다(MUST).
- 서로 다른 저장소가 기록을 연결할 수 있는 식별자를 공유해서는 안 된다(MUST NOT).

Rationale: 이 서비스가 다루는 것은 발달장애인 가구의 건강·장애·가구구성이며 모두 민감정보다.
응답 조합만으로도 재식별 여지가 있으므로, 수집하지 않는 것이 유일하게 확실한 보호책이다.

### IV. 재현성과 외부화된 설정

동일한 모델 버전 안에서 동일한 입력은 항상 동일한 결과를 산출해야 한다(MUST).

- 모델, 연계 규칙, 문항 집합에는 버전을 부여하고 판정 결과와 로그에 기록해야 한다(MUST).
- 버전 교체 시 변경 사실과 시점을 공개해야 하며(MUST), 동일 입력의 결과가 달라질 수 있음을
  함께 알린다.
- 판정과 연계에 영향을 주는 값(임계값, 안내 건수, 문구, 적합 조건)은 설정으로 외부화해야
  하며(MUST), 코드에 고정해서는 안 된다(MUST NOT).

Rationale: 같은 답을 넣었는데 다른 결과가 나오면 신뢰가 무너진다. 동시에 모델을 영원히
고칠 수 없게 만들어서도 안 되므로, 재현성의 범위를 버전 단위로 명확히 한정한다.

### V. 컨테이너 없는 코드 전개 (NON-NEGOTIABLE)

서비스 구현을 위한 기술 요소를 Docker 이미지나 컨테이너로 도입해서는 안 된다(MUST NOT).

- 모든 구성 요소는 프로젝트 폴더 안의 코드와 선언적 설정으로 전개해야 한다(MUST).
- 외부 데이터베이스 접속은 애플리케이션 드라이버로 직접 수행한다(MUST).
- 이 원칙은 `Intent-Plan.md`의 절대규칙에서 비롯되며, 같은 문서의 배포 항목에 언급된
  Docker 컨테이너 패키징보다 우선한다.

Rationale: 프로젝트 소유자가 명시한 절대규칙이다. 실행 환경을 프로젝트 폴더 안에 두면
인수인계와 재현이 단순해진다.

## 기술 및 데이터 제약

**스택** — 프론트엔드는 Vue 3 + TypeScript + Vite + Pinia, 백엔드는 Node.js 20 LTS +
Express + TypeScript, 데이터베이스는 MariaDB(mysql2 드라이버)를 사용한다. 다른 스택을
도입하려면 개정 절차를 거쳐야 한다.

**학습 데이터** — 2024 발달장애인 일과 삶 실태조사 기반 정제 테이블을 사용한다. 원자료
전체 문항을 대상으로 한 재선별은 명시적 개정 없이 범위에 포함하지 않는다.

**척도 방향** — 돌봄부담 내부 라벨은 **1이 최고부담, 5가 부담 없음**이다. 숫자가 작을수록
부담이 크다. 이 방향은 실데이터로 확인된 사실이며, 임계값 비교와 화면 표시를 작성할 때
반드시 확인해야 한다. 내부 라벨은 이용자에게 노출하지 않는다(원칙 II).

**디자인** — `Intent-Tasks.md`가 지정한 디자인 템플릿을 프로젝트 전반에 일관되게 적용한다.

## 개발 워크플로 및 품질 게이트

**단계 순서** — `specify` → `clarify` → `plan` → `tasks` → `implement` 순으로 진행한다.
미해결 모호성이 남은 상태에서 `plan`으로 진입하지 않는다(SHOULD NOT). 탐색적 스파이크로
건너뛰는 경우 재작업 위험을 명시적으로 기록한다.

**측정 가능성** — 모든 Success Criteria에는 측정 수단이 배정되어야 한다(MUST). 측정 수단을
정의할 수 없는 지표는 범위에서 제외하거나 관측 가능한 형태로 재정의한다.

**독립 전달** — User Story는 우선순위별로 독립 전달 가능해야 한다(MUST). 상위 우선순위
스토리가 하위 스토리의 완성을 전제하는 요구사항은 하위 스토리로 이동한다.

**단일 편집자** — 명세 문서(`spec.md`, `plan.md`, `tasks.md`)는 한 번에 한 세션에서만
편집한다(MUST). 동시 편집은 병합 충돌과 결정 충돌을 만든다.

**위반 기록** — 원칙을 위반해야 하는 경우 `plan.md`의 Complexity Tracking에 위반 항목,
필요한 이유, 기각한 단순 대안을 기록해야 한다(MUST). 기록 없는 위반은 허용되지 않는다.

## Governance

이 헌법은 프로젝트의 다른 관행과 문서에 우선한다. 충돌이 있으면 헌법이 이긴다.

**개정 절차** — 개정은 변경 사유, 영향 범위, 의존 산출물 갱신 계획을 함께 제출해야 한다.
개정이 승인되면 같은 커밋에서 의존 템플릿(`plan-template.md`, `spec-template.md`,
`tasks-template.md`)의 정합성을 확인하고 필요한 변경을 반영한다.

**버전 정책** — 시맨틱 버저닝을 따른다.
- MAJOR: 원칙 삭제, 또는 기존 산출물을 무효화하는 재정의
- MINOR: 원칙·섹션 신설, 또는 지침의 실질적 확장
- PATCH: 표현 정리, 오탈자, 의미를 바꾸지 않는 다듬기

**준수 검토** — `plan` 단계의 Constitution Check에서 전 원칙을 점검한다. 게이트는 Phase 0
착수 전과 Phase 1 설계 후 두 번 통과해야 한다. NON-NEGOTIABLE로 표시된 원칙(I, III, V)은
Complexity Tracking 기록으로도 면제되지 않는다.
